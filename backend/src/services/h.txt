# Phase 10.30 — Approval Resume (execution after decision)

> Root: dc62d2e `AI: gate privileged tools behind user approval`
> This phase: `AI: resume instruction after approval`

## Goal

Continue an interrupted AI instruction turn after the user approves the gated
tool call. The approved tool operation — and ONLY it — executes, consumes the
approval, and the turn resumes inside the approval's own conversation, on the
conversation's persisted round budget.

## What changed

### Persistence (`ai_tool_approvals`)
- Repo `consumeToolApproval(userId, approvalId, now)`: a transaction that
  verifies ownership, requires `approved` status, and backdates `expires_at`
  to `now`. The DB CHECK forbids a `consumed` status, so the row stays
  `approved` — but every later executable guard treats the backdated window
  as expired, so any replay fails closed. Missing/foreign → 404
  (`ToolApprovalNotFoundError`); not-`approved` → 400
  (`ToolApprovalAlreadyResolvedError`); elapsed window → sweeps to `expired`
  then throws `ToolApprovalExpiredError`.
- Service `consumeToolApproval(userId, approvalId, now = now())`: input
  validation (non-empty user, UUID id), delegates to the repo.

### Loop seeding (`agentLoop`)
- `runAgentLoop` accepts optional `initialToolResults` + `initialToolRounds`
  (non-negative integer). Seeded results are served as already-executed
  first-request context and the seeded round count is compared against
  `maxToolRounds` from the very first provider request. Default behavior
  (omitted) is byte-for-byte unchanged: empty results, round zero.

### Resume turn (`persistentAgentTurn`)
- `PersistentTurnInput.resumeApprovalId` enters resume mode.
- Load phase (before anything runs): resolve the approval OWNED by the
  authenticated user (missing/foreign → 404); a supplied `conversationId`
  must equal the approval's own conversation (else 400); assert the approval
  is currently executable (rejected/expired/consumed → 400, nothing runs);
  load the approval's conversation and adopt its persisted `maxToolRounds`
  as this turn's bound. This mirrors Phase 10.28D (approval resolution) and
  Phase 10.8/10.9 (conversation ownership via `loadAgentConversationState`).
- Execute phase (inside the turn's try): the approved operation runs ONCE
  through the UNCHANGED `invokeTool` gate → policy → handler → executor
  pipeline with the approval's id (`approvalId`) and the approval's own
  persisted conversation/message context. The caller supplies NO arguments —
  only the approval's exact stored, validated arguments execute (this is the
  caller-input-ignored contract of the Phase 10.28C EXECUTE path). The result
  is recorded as this turn's first round (`callId = approval.id`), the
  approval is consumed immediately (best-effort, so a consume failure can
  never mask an already-executed turn), and the eager transcript is committed
  via the same `beginAgentTurn` → `completeAgentTurn` path as any round.
- Loop phase: the executed result is seeded (`initialToolResults`,
  `initialToolRounds: 1`) so the provider's first request already carries the
  result and the turn continues from round one — bounded by the
  conversation's persisted `maxToolRounds`, never beyond it. The normal
  failure compensation (`cancelAgentTurn`) applies on any later failure.

### Instruction contract (`aiInstructions`)
- Body gains optional `approvalId` (UUID-shaped; malformed → 400; never a
  substitute for the required `instruction`). Anything else is still
  rejected — the strict-body rule and identity isolation are unchanged.
- `mapAgentTurnError` maps resume outcomes for the HTTP layer:
  - `ToolApprovalNotFoundError` → 404 `common/not-found` (foreign equivalent
    to missing),
  - `ToolApprovalExpiredError` / `ToolApprovalNotExecutableError` → 400
    `common/bad-request` (rejected / expired / consumed never execute),
  - `AppError.badRequest` (conversation mismatch) and the existing agent-loop
    → 502 mapping pass through unchanged.
